# Linux 用户与工作区协作方案

本文记录下一阶段的产品与实现方案。它不改变[当前模型](computer-runtime-identity-model.md)的事实描述；本文标为“拟实现”的行为尚未上线。

最新调整：账号接入已拆为不依赖凭据的账号创建/验证，以及独立的个人凭据读取、写入与守护进程启动，见[凭据指南](../engineering/linux-user-credentials-guide.md)。下文原方案中的“先保存凭据”顺序以该调整为准。

## 决定与边界

- 一个 Multica 用户可在不同 Computer 上拥有多个 Linux 用户，也可在**同一台 Computer 上**拥有多个不同用户名的 Linux 用户。账号以 `(computer_id, username)` 区分，每个受管账号只有一个已验证的 Multica 用户所有者；不能仅凭知道用户名接管别人的账号。
- 多名 Multica 用户可加入同一工作区，各自使用自己的 Linux 用户和运行时。加入工作区不直接共享 Linux 密码、home、模型密钥、Git 凭据或账号管理权。但账号所有者授权其他成员调用绑定在本人运行时的智能体后，执行仍在所有者的 Linux 用户权限下进行，可能使用该账号可访问的本地文件和凭据；授权调用时须让所有者知晓这一后果。
- 同一个任务允许多名成员参与：评论、回复、@成员、@有权调用的智能体、修改任务和查看运行记录。任务的单一“负责人”只表示当前责任归属，不限制其他成员参与；需要多条独立责任线时使用子任务。
- 工作区可不关联任何 Linux 用户，也可接入多名成员各自提供的运行时。创建工作区时选择本人已有的 Linux 用户或创建新的 Linux 用户是**可选的初始接入步骤**，不是工作区的唯一账号字段。
- 这一阶段沿用一个受管 `computer_binding` 同时只关联一个工作区的限制。已绑定其他工作区的 Linux 用户不能直接再接入新工作区；需要先移除旧工作区的受管 daemon，再按现有开通流程重新接入。跨工作区同时复用同一 Linux 用户另行设计，不在本方案中增加账号、授权或关联表。
- Git 提交沿用该 Linux 用户的 Git 身份配置和代码评审；本阶段不增加提交签名或可信身份追溯系统。

## 现状与差距

| 领域 | 现状 | 本阶段工作 |
| --- | --- | --- |
| 账号标识 | `computer_binding` 包含 `computer_id`、`username`、`user_id`、`workspace_id`；`(computer_id, username)` 唯一。 | 保留模型与唯一约束；界面按 Computer 和用户名展示多个账号，不以用户 ID 或 Computer ID 合并。 |
| 个人账号管理 | “设置 → 我的运行环境”已有开通、同步、升级、移除、账号详情和 CLI 管理。 | 把账号列表、账号操作和个人凭据组织成清晰的 Linux 用户管理入口；保留 CLI 在对应账号下管理。 |
| 工作区管理 | 工作区已有创建、成员、项目、任务、运行时及权限管理。 | 创建完成后提供可跳过的“接入我的运行环境”；工作区设置展示已接入的运行时及其所有者，不提供他人 Linux 账号的密码或管理操作。 |
| 协作记录 | 任务、评论、项目和智能体属于工作区；运行时有所有者与私有/公开范围。 | 沿用现有协作对象与授权，不新增“任务参与者”或“共享 Linux 账号”实体。 |

## 用户流程

1. 用户注册或受邀加入后可直接进入工作区。Linux 用户初始化是可跳过的上手引导，不参与注册或工作区创建事务。
2. 在个人设置的 Linux 用户管理入口，用户选择 Computer、输入 Linux 用户名并准备个人凭据。列表可同时显示同一 Computer 下的多个账号；每个账号独立展示状态、绑定工作区、CLI 与操作历史。
3. 创建工作区时，先完成现有工作区创建。成功后可选择“接入运行环境”：选择本人已有且可用于该工作区的账号，或选 Computer 并输入新用户名；默认允许跳过。先完成个人凭据校验，再调用现有开通接口，以新工作区 ID 建立绑定；成功后再引导安装 CLI、启动或检查 daemon。接入失败保留已创建的工作区，展示操作状态和重试入口。
4. 已在其他工作区使用的本人账号应显示但不可选。界面给出下一步：先到原工作区移除该账号的受管 daemon，确认操作完成后再返回新工作区接入；说明移除会中断原工作区依赖该账号的执行能力，但不会删除 Linux 账号。不自动迁移、删除账号或覆盖原绑定。若同一 Computer 上另有用户名，可选择那个账号接入。
5. 其他成员接受邀请后，直接参与同一批任务、评论与项目。他们可以接入自己拥有的运行环境；调用别人的智能体由智能体 Access 决定，能否把自己的智能体绑定到别人的运行时由运行时所有者设置的可见范围决定。

对新工作区选择“已有账号”时，当前 `claimComputerBindingSQL` 允许本人已验证且处于 `removed` 或 `detached` 的 binding 通过 `provision` 改绑；仍服务于其他工作区的账号不可直接选择，同工作区的重试也不等于跨工作区迁移。归档账号不在普通列表中；未验证的失败记录尚不代表账号所有权，应走凭据验证与开通流程。最终候选还须结合账号状态、Computer 可用性、个人凭据和进行中的操作判定，完整判定表见实施任务 1。

同一 Computer 的 `(computer_id, username)` 只对应一条 binding。若该用户名已有其他已验证所有者，另一位成员不能用同名账号接入；界面应提示选择其他用户名或联系管理员，不透露原所有者身份。当前开通接口把占用和操作进行中合并为同一个 `409`，实施前须明确可安全区分的错误契约，不能仅靠前端猜测原因。

Web 与 Desktop 的新建工作区流程沿用各自现有入口；Desktop 的创建阶段仍在 `WindowOverlay`。创建完成后，接入引导在目标工作区上下文展示为可关闭的共享界面，并保留从设置再次进入的入口；具体采用对话框还是页面内提示，在任务 1 核对现有欢迎引导后决定，避免两个引导同时弹出或跳过后无法找回。

工作区关联的是执行能力，不是对 Linux 账号的所有权转移。移除工作区成员应继续停用其运行时和相关智能体；删除工作区应保留远端 Linux 账号，并按现有流程解除绑定。账号的 `remove`、`archive` 与 `delete_user` 继续是不同操作，不能由工作区删除或成员退出隐式触发 `userdel`。

## 数据、执行与代码同步

- PostgreSQL 中的工作区成员、任务、评论、项目和运行记录是协作数据。现有事件和查询缓存让成员看到更新；无需同步各 Linux 用户的 home。
- 项目可以引用工作区仓库或项目仓库。不同 Linux 用户的 daemon 各自在自己的工作目录中获取代码；代码通过 Git 远端、分支和 PR 汇合。本地目录资源只对指定 daemon 生效，不能假设别的账号或机器可访问同一路径。
- 同一个任务可有多条评论和多次智能体运行，但只有一个当前负责人。@智能体不会改负责人；多人同时改任务字段时仍可能产生覆盖，不能把任务页面描述为实时共同编辑器。
- 对绑定运行时的智能体，其运行使用该智能体绑定的运行时，与任务负责人是成员还是智能体无关。Agent Access 决定谁能触发调用；运行时可见范围决定谁能把智能体绑定到该运行时，不能用运行时可见性代替调用授权。
- Multica 记录任务和评论的作者及运行归属；Git author 来自执行环境配置。二者用途不同，不承诺仅凭 Git author 证明发起人身份。

## 实施顺序与验收

1. **个人账号入口。** 整理现有“我的运行环境”列表与详情，确保同一用户在同一 Computer 的两个不同 Linux 用户可分别开通、安装 CLI、查看状态和清理；保持查询按当前用户授权。
2. **工作区创建后的可选接入。** Web 与 Desktop 共用引导 UI 和 Query/mutation；工作区创建成功后才提交 binding 操作，不修改工作区创建 API 的原子语义。无 Computer、无可用账号、已有其他工作区绑定、开通失败及跳过都有明确状态。
3. **工作区执行资源可见性。** 在工作区现有运行时页面展示所有者和可用范围；成员只管理自己的 Linux 用户与凭据。开放运行时或智能体访问时，说明被授权的执行可能使用所有者账号可访问的文件和凭据。验证 Agent Access、运行时可见性、成员移除和工作区删除路径。
4. **验收。** 两个人在同一任务下评论、@成员及有权调用的智能体；两人各自的 Linux 用户和凭据互不可见；同一用户在同一 Computer 的两个 Linux 用户各自操作；工作区创建后接入失败不删除工作区；已绑定账号不会被新工作区静默接管。远端建号、安装和 daemon 行为仍需在非生产 Computer 上验收。
